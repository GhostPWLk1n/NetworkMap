# Правила работы Codex и Claude Code в NetworkMap

Общие правила проекта хранятся в этом файле. Claude Code подключает их через `CLAUDE.md`.

## Git и публикация

- Перед изменениями проверь текущую ветку, `git status` и адрес `origin`. Сохраняй правки пользователя и добавляй в коммит только файлы текущей задачи.
- После проверки всегда коммить и публикуй изменения в GitHub обычным `git push`. При последовательной работе по умолчанию используй `main` репозитория `GhostPWLk1n/NetworkMap`. Если пользователь указал другую ветку или работу через PR, публикуй в соответствующую ветку.
- Если удалённая ветка ушла вперёд, сначала сравни истории и сохрани обе стороны. Не используй принудительную отправку и не переписывай опубликованную историю без явного указания пользователя.
- После отправки проверь SHA удалённой ветки и сообщи SHA опубликованного коммита. Если публикация заблокирована, сообщи причину и состояние локального коммита.
- Для анализа и ведения бэклога создавай коммит только при наличии изменений в файлах репозитория. Если пользователь просит собрать задачи без разработки, ограничься GitHub Issues.
- В Git добавляй исходники, конфигурацию с примерами значений и документацию. Рабочие базы, выгрузки инвентаризации, архивы, `dist`, `node_modules`, `.env`, ключи и токены остаются локально.

## Совместная работа Codex и Claude Code

- Перед началом или при возврате к задаче выполни `git fetch origin`. Сверь рабочую ветку, базовый коммит и изменения в рабочей папке с последней передачей задачи или GitHub Issue. Если удалённая ветка изменилась, сначала прочитай новые коммиты.
- При параллельной работе согласуй, кто ведёт каждую задачу и какие файлы меняет. Каждому исполнителю выделяй отдельную рабочую папку Git (`git worktree` или отдельный клон) и ветку от актуальной `origin/main`. Если задачи требуют правок одних и тех же файлов, выполняй правки последовательно или передай их одному исполнителю.
- Публикуй проверенные коммиты параллельной задачи в её ветку. Согласуй, кто интегрирует изменения в `main`. При интеграции сверь изменения с актуальной `origin/main` и повтори затронутые проверки после объединения.
- При передаче работы укажи номер задачи, ветку, SHA опубликованного коммита, кратко опиши изменения, проведённые проверки и оставшиеся шаги. Если второму агенту поручено ревью, он проверяет опубликованный diff и сообщает замечания с привязкой к файлам. Исполнитель вносит исправления в свою ветку.

## Роли при передаче задачи через GitHub

- **Claude Code — разработчик.** Берёт согласованное задание из GitHub Issue, создаёт ветку от актуальной `origin/main`, реализует изменения и выполняет первичные проверки. Публикует ветку и открывает PR в `main` со ссылкой на Issue, описанием изменений и результатами проверок. Отвечает на замечания и отправляет исправления в ту же ветку.
- **Codex — тимлид и тестирующий.** Формулирует задание и критерии приёмки в Issue, проверяет опубликованный PR, воспроизводит сценарии на отдельной тестовой базе и фиксирует результаты и замечания в PR. Проверяет исправления по последнему SHA. Приёмку и слияние этой задачи в `main` ведёт Codex после прохождения проверок и устранения блокирующих замечаний.
- Issue хранит актуальное задание и критерии приёмки. PR хранит реализацию, результаты проверок и решения по замечаниям. При существенном изменении требований обновляй Issue, чтобы следующий исполнитель мог продолжить работу по репозиторию.

## Журнал изменений

- Основной журнал проекта — `CHANGELOG.md`. Разработчик добавляет изменение, заметное пользователю или важное для обновления, в верхний раздел `## [Не выпущено]` вместе с реализацией. Создай раздел, если его ещё нет. При работе через PR запись входит в тот же PR.
- Используй существующие рубрики журнала, например `Добавлено`, `Изменено`, `Исправлено` и `Схема БД`. Кратко опиши результат для пользователя и условия обновления, если они есть. Добавь ссылку на GitHub Issue, когда задача заведена. Промежуточный ход работы и результаты проверок фиксируй в Issue и PR.
- При приёмке Codex сверяет запись с фактическим поведением и проверяет, что в разделе нет дублей. При слиянии параллельных PR сохраняй записи обеих задач.
- При выпуске Codex переносит записи из `Не выпущено` под заголовок `## [X.Y.Z] — YYYY-MM-DD`, используя согласованный номер версии и фактическую дату выпуска. Готовь краткую сводку в `RELEASE_NOTES.md`, когда она входит в задачу на выпуск.

## Версии и сборка для выпуска

- Используй [SemVer](https://semver.org/): `MAJOR` (`2.0.0`) для несовместимых изменений, `MINOR` (`1.50.0`) для новых совместимых возможностей и `PATCH` (`1.49.1`) для совместимых исправлений. Совместимость оценивай по открытию существующих баз и работе поддерживаемых клиентских и серверных сценариев. Добавление функции с автоматической миграцией существующей базы относится к `MINOR`, если прежние сценарии сохраняются.
- Перед сборкой установщика для передачи пользователю сравни содержимое выпуска с предыдущей выпущенной версией и выбери повышение по самому существенному изменению. Применяй повышение один раз на выпуск. Для проверочных сборок из веток PR достаточно обозначать SHA коммита.
- В одном коммите выпуска синхронизируй версию в `package.json`, корне и записи `packages[""]` файла `package-lock.json`, `server/package.json` и заголовке выпуска в `CHANGELOG.md`. Перед передачей проверь, что имя установщика и версия внутри приложения совпадают с манифестом. Для нового состава выпуска используй новый номер версии.

## Изменения и проверка

- Сохраняй совместимость с существующими SQLite-базами. Если меняется схема, обновляй `src/main/db/schema.sql` и миграции в `src/main/db/index.js`. Проверяй новую базу и обновление существующей тестовой базы.
- Переиспользуй `src/shared/dbChannels.js` для операций с данными в Electron и по RPC. При изменении общего сценария проверяй затронутые локальный и сетевой режимы.
- Проверяй изменения через обычный пользовательский сценарий в Electron, когда затронут интерфейс. Используй временный профиль и тестовые данные. Рабочую базу не используй для проверок без согласования.
- Перед коммитом проверь `git diff --check`, синтаксис изменённых файлов JavaScript и основные затронутые сценарии. В итоговом сообщении укажи, что проверено, и отметь существенные ограничения проверки.
