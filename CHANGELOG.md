# Журнал изменений

Формат по мотивам [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/).
Версия отображается в шапке приложения и берётся из `package.json`
(`app.getVersion()`).

## [1.45.0] — 2026-09-10

### Добавлено
- **Цветной контур занятости на плане — как в Google Таблицах.** Раньше
  второй клиент, пытавшийся зарезервировать уже занятый объект, не
  получал вообще никакого сообщения — просто ничего не происходило.
  Теперь: (1) занятый объект обведён цветной рамкой ещё до попытки его
  редактировать — у каждого держателя свой стабильный цвет (хэш по
  hostname, палитра из 8 цветов, без красного/жёлтого/оранжевого — они
  уже заняты статусами и выделением в этом же интерфейсе); (2) попытка
  захватить занятый объект даёт явный toast с именем того, кто его
  держит, а не только тихую надпись в углу инспектора.
- **Перебор адресов маячка** — хост публикует адреса всех своих сетевых
  интерфейсов, включая виртуальные (Hyper-V/WSL/VPN/Docker), и заранее
  угадать, какой из них реально доступен с конкретного клиента, нельзя
  надёжно (виртуальные диапазоны пересекаются с настоящими корпоративными
  сетями). Вместо гадания — клиент теперь честно пингует каждый адрес по
  очереди при клике «Подключиться как клиент» и использует первый реально
  ответивший, с индикацией «Проверяем X.X.X.X…» в процессе.

### Исправлено
- **Хост мог узнать о чужой блокировке только через фоновый тик, до
  10 секунд задержки, даже держа её сам.** Немедленный запрос/освобождение
  блокировки (`requestLock`/`releaseLock`) возвращали успех клиенту как
  обычный IPC-ответ, но не рассылали событие, по которому обновляется
  визуальный контур — из-за этого сам держатель блокировки увидел бы свой
  собственный контур с задержкой, а не сразу после захвата. Теперь
  рассылается немедленно, вместе с ответом от хоста.
- **Устаревший текст в настройках БД** — раньше честно (но уже неверно)
  утверждал, что клиенты не могут редактировать данные ни при каких
  условиях. Переписан под текущую реальность: хост может разрешить
  изменения по модели «взялся — ходи», занятые объекты видно контуром,
  хост может отключить конкретного клиента принудительно.

Проверено честно через настоящие отдельные процессы Electron: два
клиента одновременно резервируют один и тот же объект — держатель видит
свой контур сразу же, посторонний клиент (без попытки захвата) видит его
в течение обычного фонового цикла, попытка захвата даёт toast с точным
именем держателя. Перебор адресов маячка — напрямую через реальную
функцию проверки связи: два заведомо недостижимых тестовых адреса
(TEST-NET, RFC5737) корректно отклонены, рабочий адрес найден и выбран,
даже стоя вторым в списке, а не первым.

## [1.44.0] — 2026-09-10

### Добавлено
- **Настоящая вертикальная ручка изменения ширины инспектора** — узкая
  полоска между рабочей областью плана и инспектором, тянуть можно по
  всей высоте, а не только за нижний правый угол, как было раньше
  (нативный CSS `resize: horizontal` даёт ручку исключительно в углу —
  неудобно на высокой канве, приходится каждый раз тянуться вниз).
  Подсветка при наведении, курсор `col-resize` на всей длине. Ширина
  сохраняется между запусками.

Проверено честно через настоящий Electron: перетаскивание мышью из
СЕРЕДИНЫ высоты ручки (не из угла) корректно меняет ширину, ограничения
по минимуму и максимуму соблюдаются, значение сохраняется и
восстанавливается между запусками.

## [1.43.1] — 2026-09-10

### Исправлено
- **«Стать хостом» тихо переключал БД на путь по умолчанию** — вместо
  того чтобы оставить реально открытый файл (сетевой путь или любой
  другой, ранее выбранный через «Подключиться к существующему файлу»).
  Диалог подтверждения честно обещал «текущий файл БД останется у вас
  локально», но кнопка всегда передавала `null` вместо настоящего пути —
  после перезапуска приложение открывало
  `AppData/Roaming/network-map-app/data.db`, будто ничего другого никогда
  не выбиралось.
- Теперь перед переключением в режим хоста берётся актуальный путь через
  `getDbInfo()` и передаётся как есть. Единственное исключение — переход
  из клиентского режима: там своего открытого файла физически нет (клиент
  свою БД не открывает вообще), так что откат на путь по умолчанию в этом
  случае — единственный разумный вариант, и он сохранён.

Проверено честно через настоящий процесс Electron с реальным нажатием
кнопок в интерфейсе (не через прямой вызов API): приложение запущено с
нестандартным путём к БД, открыта модалка настроек, нажата кнопка «Стать
хостом» и подтверждён диалог — сохранённый `db-config.json` содержит
ровно тот путь, что был реально открыт до этого, а не путь по умолчанию.

## [1.43.0] — 2026-09-04

### Исправлено
- **Хост мог перехватить зарезервированный клиентом объект без единого
  предупреждения.** Модель «взялся — ходи» (v1.42.0) проверялась только
  для записей, приходящих по сети от клиентов — локальные вызовы самого
  хоста вообще не проходили через `writeLocks`, будто блокировок не
  существует. Теперь хост тоже уважает чужие резервирования: попытка
  локально отредактировать или переместить объект, который держит
  клиент, отклоняется с понятным сообщением, кто именно сейчас его
  редактирует.

### Добавлено
- **Хост видит занятость так же, как её видит клиент** — не только по
  факту отказа при попытке что-то сохранить. В инспекторе плана —
  сообщение «🔒 Сейчас редактируется клиентом «X»»; перетаскивание
  такого объекта мышью не срабатывает вообще, точно как у клиента без
  права. Переиспользован тот же живой снимок блокировок, что уже
  доставлялся клиенту на каждый heartbeat — просто теперь он приходит
  и в собственное окно хоста при каждом изменении.
- **Экстренное отключение клиента** — в списке подключённых клиентов
  (⚙️ Настройки БД) у каждого теперь кнопка «⛔ Отключить», с
  подтверждением. Снимает все блокировки этого клиента немедленно.
  Поскольку это обычный stateless HTTP (разрывать физически нечего),
  «отключение» — это явный сигнал: клиент узнаёт о нём на следующем же
  heartbeat, теряет свои резервирования в интерфейсе и получает тост
  об этом, вместо того чтобы молча попытаться перезахватить то же самое.

Проверено честно через настоящие отдельные процессы: клиент захватил
блокировку и на данные устройства (карточка), и на его позицию на плане
(инспектор) — раздельно, поскольку это независимые уровни. Хост получил
отказ на обе попытки локально вмешаться, с точным указанием, кто держит;
в инспекторе увидел то же сообщение о занятости, что видит клиент;
настоящая попытка мышью не сдвинула объект ни на клетку. После
принудительного отключения через настоящую кнопку в интерфейсе — хост
получил право писать и двигать, а клиент на следующем heartbeat
подтверждённо потерял и то, и другое.

## [1.42.1] — 2026-09-04

### Исправлено
- **Хост не видел изменений, внесённых клиентом.** Живые обновления
  (v1.40.0–v1.41.0) работали только в одну сторону: клиент узнавал об
  изменениях хоста через опрос журнала. Когда клиенты получили право
  редактировать (v1.42.0), хост про их правки не узнавал вообще — его
  собственный интерфейс ни на что не был подписан, оставаясь актуальным
  только для действий, сделанных через сам хост.
- Добавлено обратное уведомление: после успешной записи, пришедшей от
  клиента по сети, хост сразу (не дожидаясь опроса) получает то же самое
  событие `data-changed`, что уже умел обрабатывать интерфейс клиента —
  переиспользован тот же журнал и тот же обработчик, ничего нового
  придумывать не пришлось.
- По пути найдена и исправлена ещё одна реальная ошибка в точке отсчёта:
  первая попытка сделать это в лоб (запомнить последний id журнала сразу
  при старте хоста) приводила к тому, что первая же правка клиента
  показывала хосту заодно **всю** его собственную историю действий,
  сделанных локально между стартом хоста и этим моментом — так что
  точка отсчёта теперь ещё и синхронизируется на лету после каждого
  локального действия самого хоста, не только при подключении клиента.

Проверено честно через настоящие отдельные процессы Electron: хост
подписался на `data-changed`, клиент запросил право, отредактировал
устройство через настоящую форму — хост получил ровно одно событие с
точным описанием правки, без единой ложной записи о собственных более
ранних действиях, и его `devicesCache` реально обновился.

## [1.42.0] — 2026-09-04

Клиенты больше не обязательно read-only. Хост может разрешить редактирование
по модели «взялся — ходи»: кто первый открыл объект для правки, тот и
держит право на него, пока не закроет или не станет неактивен.

### Добавлено
- **Глобальный тумблер у хоста** («⚙️ Настройки БД» → «Совместный доступ»)
  — «Разрешить клиентам вносить изменения». Выключен по умолчанию —
  ничего не меняется для тех, кто не включил. Персистентен, переживает
  перезапуск хоста.
- **Временные блокировки на редактирование** (`writeLocks.js`) — живут
  только в памяти хоста, не в БД (после перезапуска хоста сбрасываются
  сами, как и задумано). Два независимых уровня: `device` (данные
  устройства — hostname/IP/владелец) и `plan_item` (структура на плане —
  позиция, состав группы, удаление). Держа блокировку на группу, чужой
  клиент не может менять её состав — но данные устройств уже внутри неё
  защищены отдельно, своей блокировкой.
- **Продление и освобождение — через уже существующий heartbeat**, без
  отдельного механизма: клиент раз в 10 секунд (и сразу при подключении,
  не дожидаясь первого тика) сообщает хосту, что реально держит открытым
  — то, что пропало из списка (закрыли карточку), освобождается само, без
  отдельного действия. Явные кнопки «Запросить право» / «Освободить»
  дают мгновенный результат, не дожидаясь ближайшего тика.
- Протухание за 60 секунд без единого пинга — клиент пропал (сеть
  оборвалась, приложение закрылось не штатно) — блокировка снимается
  сама, не виснет навечно.
- **Карточка устройства на вкладке «Устройства»** — поля заблокированы,
  пока право не запрошено явно; после получения — обычная форма,
  сохранение уходит на хост как есть.
- **Перемещение устройства на плане мышью** — то же самое: без личного
  права объект просто не перетаскивается (`draggable` управляется тем же
  местом, что уже отвечало за блокировку слоёв — `isNodeLocked`, единая
  точка правки затронула заодно и режим удаления, и рисование линий).
  Кнопка «🔒 Запросить право перемещения» — прямо в инспекторе плана.
- Попытка писать в обход UI (например, напрямую через API) тоже
  отклоняется на хосте — защита не зависит от того, насколько «вежливо»
  ведёт себя клиент.
- Баннер клиента теперь честно показывает текущее состояние («хост
  разрешил изменения» / «хост пока не разрешил») вместо прежнего
  безусловного «только просмотр».

### Известное ограничение этой версии
- **Панель группы («шкафы»)** пока не подключена к блокировкам —
  устройства внутри нельзя редактировать через саму панель, даже если
  хост разрешил запись. Обходной путь уже есть: «Открыть полную карточку
  устройства» переводит на вкладку «Устройства», где редактирование
  полностью защищено блокировками. Прямая интеграция в панель —
  следующим шагом.

Проверено честно через настоящие отдельные процессы Electron, не
симуляцию: хост и до трёх клиентов одновременно. Полный цикл — тумблер
выключен → отказ; включён → захват; занято другим клиентом → отказ с
указанием, кто держит; попытка писать в обход блокировки тоже отклонена;
освобождение → доступно следующему; финальное состояние в БД подтверждает,
что прошла именно правка владельца блокировки, а не конкурента. Отдельно
— перемещение мышью: без права настоящая попытка мышью (не programmatic
API) не сдвигает устройство, с правом — сдвигает и сохраняется. По пути
найден и исправлен реальный баг: общий переключатель режима «Рисование»
перебивал персональное право, требуя от клиента двух отдельных действий
вместо одного — после фикса личного права достаточно самого по себе.

## [1.41.0] — 2026-09-04

### Исправлено
- **Перемещение устройства на плане не попадало в журнал** — ни обычное
  перетаскивание мышью, ни перемещение через API. Причина: `move()` и
  «простая» ветка `moveDeviceItemWithGrouping` (клетка назначения
  свободна, группировка не нужна) писали координаты в БД напрямую, минуя
  `auditLogRepo.log(...)`. Теперь обе ветки пишут запись вида «Устройство
  «X» перемещён(а) на плане: (3,3) → (8,8)» — с реальными координатами
  «откуда» и «куда». Заодно `setRotation()` (поворот стены/двери/лестницы)
  тоже получил запись в журнал — раньше тоже проходил мимо.
- **План у клиента не обновлялся при изменениях с хоста** — прошлая
  версия (1.40.0) показывала тост с кнопкой «Обновить план», требуя
  явного клика. Теперь обновление тихое, без участия пользователя:
  - Изменения только данных устройства/владельца (hostname, IP, статус,
    снятие/назначение владельца) — точечное обновление уже отрисованной
    иконки на месте, без пересборки канвы вообще (в т.ч. и внутри
    открытой панели группы, если устройство там).
  - Структурные изменения (устройство переместилось/появилось/пропало/
    образовало группу) — требуют полной перестройки этажа, координаты и
    состав могли поменяться как угодно. Раньше `buildStageForCurrentFloor()`
    сбрасывала зум/панораму к исходным при каждой перестройке — выглядело
    бы как внезапный «прыжок» вида при каждом чужом изменении. Теперь
    зум и позиция сохраняются перед перестройкой и восстанавливаются
    после; выделение тоже пытается восстановиться, если выбранный объект
    всё ещё существует.
  - План обновляется в фоне независимо от того, какая вкладка сейчас
    открыта — как и списки пользователей/устройств/склада/ПО, которые уже
    обновлялись так же. К моменту, когда пользователь переключится на
    план, он уже будет актуальным. Всплывающее уведомление о самом факте
    изменения осталось, просто без кнопки — обновление уже применилось
    само.

Проверено предельно честно через настоящие отдельные процессы Electron,
двумя различимыми сценариями подряд в одном прогоне: точечное изменение
(хост снял владельца) — иконка на плане клиента обновилась
(`ownerCleared: true`), а сам объект канвы остался ТЕМ ЖЕ (`stageInstanceUnchanged:
true` — подтверждённо, что полной перестройки не было). Структурное
изменение (хост разместил новое устройство) — оно появилось на канве
клиента автоматически, канва была пересоздана (`stageInstanceChanged: true`,
как и должно быть), но зум сохранился (`zoomPreservedAfterRebuild: true`) —
без единого клика пользователя в обоих случаях.

## [1.40.0] — 2026-09-04

Хост раньше формально не видел подключённых клиентов — только раздавал
им данные по запросу. И клиенты не узнавали об изменениях, сделанных
хостом (или другим клиентом... хотя писать могут только хост — но
неважно, кто менял), пока не переоткрывали нужный список вручную.
Оба пункта закрыты переиспользованием уже существующего журнала
изменений (audit_log), без отдельного механизма уведомлений.

### Добавлено
- **Хост видит подключённых клиентов.** Каждый пинг клиента (heartbeat,
  раз в 10 секунд) теперь несёт свой hostname — хост ведёт список
  `connectedClients` (протухшие записи, от кого не было пинга дольше
  25 секунд, чистятся автоматически). В ⚙️ Настройки БД → раздел
  «Совместный доступ» — живой список «Подключено (N): hostname — виден
  X сек назад», обновляется каждые 5 секунд, пока модалка открыта.
- **Живые оповещения об изменениях.** Клиентский heartbeat на каждом
  тике (пока хост доступен) проверяет журнал на новые записи с прошлой
  проверки — новый метод `auditLogRepo.listSince(id)`, тот же журнал,
  что уже был на вкладке «Журнал», отдельный механизм уведомлений не
  понадобился. Новые записи приходят в интерфейс тостом с кратким
  описанием («🔄 Устройство «X» создано»), списки пользователей/

## [1.33.0] — 2026-09-03

Сценарий «упавший хост оставляет мёртвый маячок, который нельзя ни
перезаписать, ни удалить». На реальных сетевых шарах (SMB/NTFS) политика
доступа нередко разрешает изменять/удалять файл только тому, кто его
создал (или администратору) — если хост от одного пользователя упал
без штатного завершения, у хоста от ДРУГОГО пользователя может просто
не быть прав перезаписать его маячок по тому же пути.

### Изменено
- **Маячок хоста больше не один файл на всех — у каждого хоста свой.**
  `discovery.js` переписан: путь для маячка (⚙️ Настройки БД → «Стать
  хостом») — теперь **папка**, не конкретный файл. Каждый хост при
  старте создаёт в этой папке СВОЙ уникально названный файл
  (`networkmap-host-<hostname>-<id>.json`), никогда не трогая чужие.
  Создание нового файла в общей папке почти никогда не упирается в
  чужие права — конфликтует только правка/удаление уже существующего
  файла, а не появление нового.
- Перед публикацией своего маячка хост **best-effort** чистит протухшие
  чужие маячки в папке — если удалить какой-то не получилось (нет
  прав), это тихо игнорируется и не мешает публикации собственного.
- «Подключиться к существующему файлу» теперь понимает и файл, и папку:
  если указана папка — сканирует её на маячки, показывает самый свежий
  живой (с упоминанием, сколько ещё найдено, включая протухшие).
  Диалог выбора теперь позволяет выбрать и папку тоже.

Проверено предельно честно — не через `chmod` (root его игнорирует при
удалении), а через `chattr +i`, который реально блокирует удаление файла
даже для root, максимально приближенно к правам SMB/NTFS «менять может
только создатель»: хост А публикует маячок и «падает» без очистки;
маячок становится протухшим и физически неудаляемым; хост Б стартует в
ТОЙ ЖЕ папке и успешно публикует свой маячок, не пытаясь и не имея
нужды трогать чужой файл; третий процесс подключается к общей папке и
корректно находит живой маячок хоста Б первым (протухший маячок хоста А
идёт последним), кнопка «Подключиться как клиент» подставляет именно
адрес живого хоста. Все три шага — через настоящие отдельные процессы
Electron, не симуляция.

  держит файл БД на своём локальном диске и поднимает простой HTTP
  JSON-RPC сервер (`rpcServer.js`, без внешних зависимостей — только
  встроенный `http`), раздающий доступ к тем же операциям, что и обычный
  IPC, только по сети.
- **Режим «клиент»** (⚙️ Настройки БД → «Подключиться к хосту», указать
  `ip:порт`) — свою БД не открывает вообще, все запросы уходят на хост
  по сети (`rpcClient.js`). Только просмотр — попытки создать/изменить/

  понятным сообщением; UI дополнительно показывает баннер сверху и

- Импорт (Excel, сведения о ПК из JSON) недоступен в режиме клиента —
  требует одновременно локального файла и записи в БД, что в этом
  режиме противоречиво; отключён явным понятным сообщением вместо
  путаной ошибки.

Backend проверен максимально честно — **двумя по-настоящему отдельными
процессами Electron** (не симуляция в одном процессе): хост создаёт
устройство в своей локальной БД, клиент видит его через сеть (RPC-чтение
работает), пытается создать своё устройство — отклоняется сразу с
понятным сообщением, и на хосте после теста остаётся ровно одно
устройство — попытка клиента ничего не протащила в базу. Отдельно
проверен весь UI-слой (тоже двумя реальными процессами): баннер

рассинхронизации), панель инструментов плана заблокирована.

## [1.28.0] — 2026-08-30

### Исправлено
- **Зависание при старте с недоступным/занятым сетевым путём к БД** —
  `fs.existsSync()`/`new Database()` при обращении к "наполовину
  отвалившейся" сетевой шаре могут зависнуть на уровне ОС (блокирующий

  случае не спасает, поток всё равно остаётся забит этим вызовом, и весь
  процесс Electron виснет насмерть вместе с интерфейсом. Единственный
  надёжный способ прервать такое зависание — убить процесс целиком, а не
  пытаться прервать вызов изнутри того же потока.
- Решение: рискованная часть подключения (`db-probe.js`) теперь всегда
  выполняется в отдельном одноразовом процессе с жёстким таймаутом (8
  секунд) на стороне родителя — если процесс не ответил вовремя, родитель
  принудительно убивает его (`kill()`, не JS-таймаут) и сразу открывает
  локальную копию БД по умолчанию вместо зависания, с понятным
  диалоговым окном об ошибке. Пробник запускается только если в
  настройках сконфигурирован сетевой путь — для обычного локального
  файла (стандартный случай) пробник не нужен и не запускается, старт
  идёт как раньше.

Проверено честно: реальный зависший дочерний процесс (бесконечный цикл,
неотличим по поведению от зависшего syscall) — родитель не виснет,
корректно убивает его точно по таймауту, никаких процессов-зомби не
остаётся. Полный интеграционный тест — настоящий запуск всего приложения
с заведомо недоступным сконфигурированным путём: окно открывается за
~1.9 секунды, откатывается на локальную БД, приложение полностью
работоспособно после отката.

  одном кабеле показывались цепочкой (ПК1→ПК2→ПК3), как будто каждое
  подключено к предыдущему, вместо того чтобы быть братьями под общим

  помечаются и создаются узлами-братьями, и только потом каждому отдельно
  достраивается собственное поддерево.

## [1.6.0] — 2026-08-24

### Добавлено
- **Подключение к базе данных** — кнопка «🗄 БД» в шапке открывает
  настройки: текущий путь к файлу, бейдж «по умолчанию» / «своя», и три
  действия — подключиться к существующему `.db` по любому пути (в т.ч.
  сетевому, например шаре, которую отдаёт контейнер в Docker), создать
  новую пустую БД в другом месте, или вернуться к локальной БД по
  умолчанию. Переключение сохраняется в отдельный конфиг-файл и вступает
  в силу после перезапуска приложения (сам перезапускается автоматически) —
  так проще и надёжнее, чем на лету переподключать все открытые списки,
  канву и выделения.
  - Если сохранённый сетевой путь на момент запуска недоступен (например,
    шара не примонтирована), приложение не падает — молча открывает
    локальную копию по умолчанию и показывает предупреждение (жёлтый
    индикатор на кнопке «БД» + баннер в самой модалке).
  - **Важная оговорка прямо в интерфейсе**: SQLite — файловая БД, не
    сетевой сервер; «подключение» технически означает открытие файла по
    другому пути. Для настоящей одновременной записи с нескольких
    компьютеров это ограниченно надёжно (задокументированное свойство
    самого SQLite при работе через сетевые файловые системы) — для полноценной
    многопользовательской БД в перспективе нужен был бы Postgres/MySQL,
    это отдельный, более крупный проект.
  - Весь сценарий (первый запуск на локальной БД, переключение на «сетевую»,
    отказ сети с безопасным откатом и предупреждением, восстановление
    сети) проверен напрямую на уровне БД, а открытие/содержимое модалки —
    реальным прогоном приложения под Xvfb.

## [1.0.0] — 2026-08-23

Первая поименованная версия — фиксирует всё, что было построено к этому
моменту, и с неё начинается регулярный журнал изменений.

### Добавлено
- Электрон-приложение с SQLite (better-sqlite3), пять листов: Планы,
  Пользователи, Устройства, Склад, ПО.
- **План**: канва на Konva, сетка с шагом 900, мультиэтажность (переключатель
  этажей, каждый со своей сеткой/объектами), зум (колесо мыши + кнопки),
  drag&drop размещения столов/устройств, инструменты рисования — стена,
  дверь (встраивается в существующую стену), лестница (точка + направление),
  сетевой кабель (с промежуточными точками маршрута).
- **Поиск на плане** — по hostname/IP/инв.номеру/типу, с историей запросов
  (только финальный ввод, не по каждой букве), регистр и wildcard-режим.
- **Пользователи/Устройства/Склад/ПО** — карточные списки: клик разворачивает
  карточку для редактирования, правый клик — контекстное меню (Удалить и др.),
  поиск с тумблерами Аа/* и заготовкой расширенных фильтров.
- **Владение устройством** — перетаскивание пользователя из кармана на иконку
  ПК на плане; полная история закрепления/открепления с датами.
- **Комплектующие, периферия, ПО на устройстве** — с историей установки/снятия,
  необязательной стоимостью (комплектующие и ПО), лицензионным ключом (ПО).
- **Склад** — комплектующие и лицензии ПО, снятые с устройств или добавленные
  напрямую; статус (в заказе / в наличии / выдано / списано), выдача на любое
  устройство (кнопкой или перетаскиванием), стоимость сохраняется при любом
  перемещении.
- **История статусов устройства** — включая кнопку «🔧 Сервис» для быстрой
  отправки на обслуживание.
- **«Найти на плане»** — из карточки устройства/ПО сразу открывает нужный этаж
  и подсвечивает иконку.
- **Единый поиск в инструментах плана** — одно поле фильтрует карманы
  пользователей/устройств/склада одновременно.
- **Импорт из Excel** — списка ПК с комплектующими (формат СПК): устройства,
  пользователи, история владельцев, комплектующие, периферия; строки с явным
  сдвигом колонок помечаются в отчёте, а не «чинятся» автоматически.
- Пинг устройства по IP с индикатором online/offline/timeout на карточке и
  на иконке плана.

### Исправлено
- `ReferenceError: Cannot access 'COMPONENT_TYPE_LABELS' before initialization` —
  словари подписей типов (`COMPONENT_TYPE_LABELS`, `PERIPHERAL_TYPE_LABELS`,
  `SOFTWARE_TYPE_LABELS`) были объявлены ниже места, откуда вызывались сразу
  при загрузке листа «Склад»; перенесены в начало файла.
- Валидация статуса склада (`warehouse:add`/`warehouse:update`) — раньше
  недопустимое значение тихо подменялось на `in_stock` вместо отказа; теперь
  ведёт себя как `setStatus` и выбрасывает ошибку.

### Изменено
- «Стол» перенесён из раздела «Объекты» в «Конструктив» тулбара плана.
- Добавление устройства на план переведено на тот же паттерн, что и
  пользователи: карман с перетаскиванием на канву вместо выбора в
  выпадающем списке и отдельного режима клика.
